1. 实验设计：能不能被复现和复核

不使用人造玩具题。每个任务都来自仓库里一次真实的修复提交，做法是：

  • 取真实提交：从 4 个开源仓库的历史中挑出同时改源码和测试的修复提交，改动量 2–89 行。
  • 只回滚源码、保留测试：在提交的父版本上应用该提交的测试补丁，构造“测试已写好、实现还缺失”的现场。
  • 先验证任务有效：父版本必须失败、真实修复必须通过，两个条件都满足才纳入（7 个任务全部通过该检查）。
  • 切断答案泄露：每个 run 重新克隆并截断到父提交，删除远端、标签和 reflog，再 gc，代理无法从 git 历史里找到未来修复。
  • 隔离 CEW：裸跑使用空的 CODEX_HOME；CEW 组在同一空目录上安装本仓库。两侧使用同一模型、同一提示、同一 600–900 秒超时。
  • 自动判分：目标测试全过 + 全量测试无新增失败才算完成；判分前会还原测试文件，新增测试文件另做逐字节比对，防止改测试作弊。

这组数据说明：CEW 的规则和技能确实被加载并执行了，不是“装了没生效”。 它带来的直接收益是更完整的验证动作（lint、全量测试、技能化排查）；代价是每条命令、每次读取都在重复付费。

5. 为什么完成率没有提高

七个任务里，裸跑和 CEW 都 8/8 完成，且补丁高度相似：

  • slugify-200：两侧都引入了 pending_delimiters，逻辑一致，只差一行注释。
  • humanize-346：裸跑 1 行改动，CEW 2 行（多一行注释），都通过。
  • more-itertools-1247（中等难度）：裸跑两轮分别 56 / 60 行，CEW 54 / 42 行，都能通过全量测试。

解释：这批任务的搜索空间很小，测试已经指明了期望行为，模型本身就能一次做对。 CEW 的增量价值主要出现在“需要判断、需要跨文件、需要防止漏测”的场景，而本批任务没有给这些能力留出发挥空间。 因此这是一次天花板效应下的成本测量，不能据此推断 CEW 在困难任务上无效。

6. 关于“GPT 追上 Opus 5.5”：这次没能测到

阻塞项（已确认，不是推测）：本机没有任何可用的 Claude 端点，Opus 对照组无法启动。
  • 配置的第三方网关 cpass.cc：连续返回 502 upstream connect failed，单次探测挂起约 5 分钟后失败。
  • 官方 OAuth：claude auth status 显示已登录，但在干净 HOME 下实际返回 Not logged in；“已登录”来自失效网关的 token，不是官方凭据。
  • 备用聚合网关 llm.goaichat.top：API_KEY_EXPIRED。

因此本报告只能回答“CEW 对 GPT 有没有用”，不能回答“CEW 能不能让 GPT 追上 Opus 5.5”。 任何声称“追平”的结论，在这次数据里都没有依据。

端点恢复后，用同一套脚本补跑即可：

cd /Users/xu/project/repos/claude-everything-Workflow
# 1) 复制评测脚本：cp -r docs/eval/tools /tmp/cew-eval/tools
# 2) 确认 claude 能跑通：
claude -p "ok" --model claude-opus-5-5 --output-format json
# 3) 跑 Opus 两格（每格 7 个任务）：
python3 tools/run_trial.py --task slugify-200 --cell opus-base
python3 tools/run_trial.py --task slugify-200 --cell opus-cew

判定“追平”的口径建议提前写死：在同等 token 预算下，GPT+CEW 的完成率与 Opus 裸跑的差距 ≤ 10 个百分点； 而不是只看单次最好成绩。

7. 下一步：把评测做成能指导决策的东西

  1. 先筛题，再跑题。用裸跑筛 40 个真实 issue，只保留 GPT 失败率 ≥ 50% 的题。当前这批题对 GPT 太简单，测不出上限。
  2. 难度分层。单文件修复 / 跨文件修改 / 需求模糊的功能开发，各 5 题 × 2 次重复；报告分层结果，不混在一起平均。
  3. 等成本比较。给 CEW 和裸跑相同的 token 预算，比较“每 10 万 token 解决多少题”，否则 CEW 永远可以用更多算力换同样的结果。
  4. 盲评代码质量。测试全绿只能证明行为正确，证明不了可读性。把两侧补丁匿名化后交给独立评审（模型 + 人工抽查），按可读性、范围控制、约定一致性打分。
  5. 给 CEW 做“短路”。当前 8/8 的小修复都加载了 3–5 个技能和 1–5 份规则。若路由能识别“单文件、测试明确”的短路径，预计可砍掉一半以上的额外 token。

8. 局限

  • 样本量小：7 个任务、每格 8 次运行，只有 1 个任务做了 2 次重复；不足以做统计显著性检验。
  • 任务偏简单：全部是单文件或少量文件的 bug fix，测试已给出，存在明显天花板效应。
  • 只测了 Codex 宿主：CEW 同时支持 Claude Code，但本机 Claude 端点不可用，Claude 宿主未覆盖。
  • 测试对代理可见：更接近 TDD 场景，不等同于“隐藏测试”的 SWE-bench 设定。
  • 外层环境限制：Codex 的内层沙箱与 WorkBuddy 沙箱冲突，两侧都改为直接执行；这可能略微放大代理的探索行为，但对两组一致。
