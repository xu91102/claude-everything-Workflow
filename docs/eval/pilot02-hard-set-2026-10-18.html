3. 实验二：把测试藏起来，只掉 2 题

做法：checkout 只保留父提交源码，测试在评分时才注入；提示词明确说明“仓库不含该问题的测试， 会有隐藏测试验证”，禁止新增或修改测试。

任务类型题数基线通过说明
缺陷修复（issue 文本描述行为）1010隐藏测试没有阻止定位：读源码 + 复现即可
新增功能（只有提交标题当规格）31失败的 2 题是 API 形状无法从标题推断，属规格不足
合计1311平均 235,839 token / 20.0 条命令
不要把“隐藏测试”当成万能难度旋钮。它能挡住“照着测试写实现”，但挡不住“读懂代码后推理”。 真正失败的两题也不是因为难，而是因为题目没给出足够规格——这类失败不能算能力差异。

4. 实验三：4 题配对，CEW 多花 39% 没换来成功率

本节使用修正前的 Fast Path（2a257da）；当前版本的行为差异见第 6 节。

选 2 个基线失败题（3082c06 transpose/matmul、19726a0 metric） 和 2 个高消耗通过题（21d3d88 reshape、1b7f033 tee），隐藏测试、各 2 次重复。

过程指标解释了成本：CEW 组 8/8 读取技能、8/8 读取规则，命令数只多 5%（13.4 → 14.1）， 但每读一份技能/规则都重发上下文，token 因此 +39%。也就是说——Fast Path 没有生效， 这些题被判为“非微改”，直接落回完整流程。

怎么读这个结果：不是“Fast Path 失效”，而是它只覆盖微改任务；一旦任务看起来跨文件/跨模块， CEW 就恢复全额流程税，而这份税在这 4 题上没有换来可测收益（+1/8 在噪声内）。 下一步要治的是升级时机：先按 Fast Path 做，失败一次再读技能，而不是一开始就判定“这题不简单”。

5. 下一步（按优先级）

  1. P1-1 失败驱动升级：所有任务默认 Fast Path；第一次验证失败才读 systematic-debugging， 第二次失败才升级到 TDD/审查。这直接对应本次 +39% 的浪费。
  2. 换任务形态：小型工具库已饱和。要测能力差异，需要大仓跨模块任务（Flask/Django 级）、 issue 式模糊规格、或把 3 个独立修复合成一题。
  3. 补 Opus 臂：仍然没有可用端点；“追平 Opus”依旧无法回答。
  4. 统计升级：n=4 只能看方向；正式集需要 ≥12 题 × 3 次，并做配对检验与盲评。

7. 局限
