# 实现规范

## 架构与兼容

- 遵循目标项目的目录、分层和依赖方向；仅调整影响当前需求的职责与耦合。
- 抽象应隐藏细节、减少调用方复杂度；不为假设的复用增加接口或透传层。
- 修改共享逻辑前检查相关调用方，在共同根因位置修复，避免只修报告中的单一路径。
- 复杂度相近时，优先边界行为正确、维护成本低的方案。
- 实现、测试和类型保持局部性；跨域共用目录只承接已出现的稳定复用。
- 状态变化显式，遵循项目更新惯例；保留公共接口和既有工作流，破坏性变更需用户批准。
- 重构增量、可验证、可回退，正常与边界路径有相称验证。

## 错误处理

- 错误必须保留原因和必要上下文，不吞错、不把失败伪装为成功。
- 沿用目标项目已有的错误边界、中间件或调用方处理约定；每个错误有明确处理责任，避免逐层重复捕获和提示。
- 降级、重试与批量部分失败应显式区分；异步拒绝必须有处理方。

## 代码规模

没有项目约束时，用函数约 80 行、参数 5 个、嵌套 4 层作为职责审查提示。超限先判断职责和可读性，
不为满足数值拆出透传层，也不机械压缩代码；文件和行长由 Hook 提示，不在规则中重复维护。

## 注释

沿用项目文档惯例。注释说明不明显的原因、约束、兼容性处理、复杂算法或外部契约；
公共 API 按项目要求提供文档。自解释代码不补逐句说明，不重复类型已表达的参数和返回值。
