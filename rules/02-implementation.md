# 实现规范

## 架构与兼容

- 遵循目标项目的目录、分层和依赖方向；仅调整影响当前需求的职责与耦合。
- 抽象应隐藏细节、减少调用方复杂度；不为假设的复用增加接口或透传层。
- 局部修复只改变已授权的目标场景；修改共享逻辑前检查相关调用方，在需求范围内修复共同根因，并用相称回归证据确认非目标调用方的输入输出、错误、重试/超时及副作用不变。
- 复杂度相近时，优先边界行为正确、维护成本低的方案。
- 实现、测试和类型保持局部性；跨域共用目录只承接已出现的稳定复用。
- 状态变化显式，遵循项目更新惯例；保留公共接口和既有工作流，破坏性变更需用户批准。
- 重构增量、可验证、可回退，正常与边界路径有相称验证。

## 错误处理

- 错误必须保留原因和必要上下文，不吞错、不把失败伪装为成功。
- 沿用目标项目已有的错误边界、中间件或调用方处理约定；每个错误有明确处理责任，避免逐层重复捕获和提示。
- 降级、重试与批量部分失败应显式区分；异步拒绝必须有处理方。

## 代码规模与注释

- 没有项目约束时，用函数约 80 行、参数 5 个、嵌套 4 层作为职责审查提示。超限先判断职责和可读性，不为满足数值拆出透传层，也不机械压缩代码；文件和行长由 Hook 提示。
- 沿用项目文档惯例。注释说明不明显的原因、约束、兼容性处理、复杂算法或外部契约；公共 API 按项目要求提供文档。自解释代码不补逐句说明。

## 代码与安全禁止 (CRITICAL)

- 调试残留、类型抑制和耦合问题按目标项目标准检查；不得为掩盖真实错误添加抑制或绕过检查。`hooks/check-edited-file.js` 对 `console.log`、`debugger`、`@ts-ignore`、`@ts-nocheck` 和 `any` 的提示属于兼容性警告，需结合真实用途判断。
- 禁止硬编码密钥、API key、token、secret 或密码（改用环境变量）、SQL 字符串拼接（改用参数化）、未校验外部输入、明文密码（改用 hash）、绕过验证或质量门 Hook，以及提交调试代码。
- 危险操作必须在沙箱或等价隔离环境中执行；安全敏感改动提交前按风险检查 SQL 注入、XSS、敏感信息泄露和依赖漏洞。发现违规时立即指出问题、解释原因并提供修复方案。
