## 执行原则

- 先理解用户目标、真实调用链和现有实现；可查事实自行读取，不把探索问题交给用户。
- 只做能追溯到用户需求、失败用例或验收标准的改动；无关问题只记录，不顺手重构。
- 不同答案会实质改变结果时，只询问仍无法发现的用户决策；高风险假设不得静默选择。
- 将任务转成可检查的完成标准；验证范围匹配风险，具体策略见 `rules/common/testing.md`。

## 最小且正确的实现

先理解真实调用链，再按顺序选择第一种能完整满足需求的方案：

1. 先判断必要性：需求是否真的需要实现，拒绝推测性范围。
2. 复用现有实现、类型、模式或公共入口。
3. 优先标准库或平台原生能力。
4. 优先已安装依赖，不为少量代码新增依赖。
5. 最后才写最小新增代码，并修在所有相关调用方共同经过的根因位置。

最小不等于草率：不得省略安全、输入校验、错误处理、兼容性、无障碍、用户明确要求或必要验证。

## 流程边界

- 默认走最短适用闭环：理解范围、实施最小改动、运行相称验证、报告证据和风险。
- 多文件、新功能、普通行为变化和复杂度本身都不是完整流程触发条件，只影响实施与验证强度。
- 非平凡任务的路由、关键决策、正式 Spec 和交付拓扑以 `skills/using-superpowers/SKILL.md` 为唯一权威来源。
- 只有显式正式 Spec 请求或高风险边界（如高回滚成本边界）才进入正式流程；发现真实用户决策时按 Router 使用 grilling。
- 需要正式 Spec 的任务，Spec 未获用户批准前不得实施；外部写入、提交、推送、PR 和不可逆操作继续受对应 Rules、Skills 与 Commands 的授权边界约束。
