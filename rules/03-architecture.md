# 架构原则

## 核心原则 (CRITICAL)

- 单一职责、高内聚低耦合；接口隐藏实现细节，依赖方向清晰。
- DRY 只消除已经出现的重复，不为推测性复用创建抽象。
- KISS：优先现有模式、标准库、平台原生能力和最小正确实现。
- 状态转换保持显式；优先不可变更新，避免调用方依赖隐式副作用。
- 抽象必须降低调用方复杂度；单实现接口、未来配置和透传层默认不增加。

## 结构与局部性

- 按业务或领域组织代码，相关实现、测试和类型就近放置。
- 后端保持请求处理、业务规则、数据访问和领域模型之间的职责边界。
- 前端保持 UI 展示、状态/业务逻辑和外部请求之间的职责边界。
- 只有出现稳定的跨域复用后才抽取 `common`、`shared` 或 `utils`。

## 重构与兼容

- 只处理影响当前需求的代码异味；保留现有功能和公共接口，除非用户批准破坏性变更。
- 变更应增量、可验证、可回退；必要迁移保持向后兼容并明确退出条件。
- 正常路径和边界路径都必须有相称验证。

## 跨平台脚本

自动化脚本优先使用 Node.js 等跨平台方案，避免依赖特定 shell；调用包管理器时自动检测 npm、pnpm、yarn 或 bun，并兼容 Windows、macOS 和 Linux。
