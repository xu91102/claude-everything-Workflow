# 第一性原则与对抗性测试

把抽象原则转成可执行约束。涉及架构调整、复杂实现、重构、测试策略、质量门或高风险修改时按需读取；简单文案、格式或低风险配置改动无需加载。

## 第一性原则

开始设计或实现前，先把任务拆到不可再压缩的判断依据：

1. 明确核心目标：这次改动真正要保护或达成什么。
2. 明确不可变约束：兼容性、数据格式、公共接口、用户工作流、安全边界和运行环境中哪些不能破坏。
3. 明确优先级：正确性、可维护性、兼容性、性能、开发速度发生冲突时按什么顺序取舍。
4. 明确失败代价：最坏情况下会影响哪些用户、数据、命令、自动化或发布流程。
5. 明确成功标准：用测试、构建、类型检查、复现用例或人工验收描述可验证结果。

每条原则都必须约束具体决策，例如“保持现有命令参数兼容”优先于“接口更优雅”。

## 对抗性测试

设计验证主动寻找能打破实现的输入、状态和环境，而不是只覆盖 happy path：空输入、缺失字段、损坏配置和未知枚举；重复或并发执行、部分成功后重试；含空格、中文、特殊字符、相对路径或跨平台分隔符的路径；权限、占用、目录、磁盘和网络失败；依赖缺失、版本不匹配、外部超时或异常结构；历史数据、旧配置、用户已有改动；以及大输入、边界数值、极端长度和顺序变化。

## 工作方式

- 复杂任务在计划或实现前列出 3-7 条第一性原则，并逐条映射到实现约束或验证项。
- 行为变化优先添加能失败的对抗性用例；无法自动化时记录手工步骤和剩余风险。审查检查默认值、顺序依赖、全局状态、环境变量、缓存、时间、路径和外部服务。
- 对抗性测试暴露设计问题时先修正设计边界，再补实现；验证总结说明已覆盖的正常路径、对抗路径和未覆盖风险。
