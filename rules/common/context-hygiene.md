# 上下文卫生与 Subagent 边界

上下文不是聊天记录，而是下一轮推理需要的工作集。长任务中，搜索结果、目录列表、失败日志和被排除的分支会快速稀释有效信息；这些内容应尽量隔离、压缩和按证据回传。

## 使用 Subagent 的目的

Subagent 首先是独立工作区，其次才是并行人力。它适合处理必须探索、但不值得污染主上下文的工作：

- 影响面分析：搜索引用、调用链、配置残留、文档残留。
- 代码审查：只返回阻塞问题、证据路径和风险等级。
- 测试诊断：独立阅读失败日志，给出最小复现和可能根因。
- 安全、性能、数据库等专项审查：边界明确，输出可压缩。
- 文档一致性检查：验证 README、规则、命令和示例是否随改动同步。

不适合委派的场景：

- 子任务需要和主循环频繁协商。
- 多个阶段高度共享临时状态。
- 任务很小，委派成本高于收益。
- 子代理必须继承大量脏上下文才能行动。

## Fresh 与 Fork 的选择

| 方式 | 适用场景 | 风险 |
| --- | --- | --- |
| Fresh subagent | 搜索、审查、测试诊断、文档一致性等可用简短任务说明完成的工作 | 可能需要重新建立少量背景 |
| Fork subagent | 必须继承父会话完整约束、历史决策或复杂方案比较 | 会复制父上下文里的噪音和过期判断 |

默认使用 fresh。只有“不继承背景就会误判”的任务，才使用 fork。

## 路由契约

每个 agent 的 `description` 应写成路由契约，而不是泛泛职责。至少包含：

- 触发条件：什么场景应该使用它。
- 输入边界：它会读取哪些信息，不应读取哪些信息。
- 输出契约：返回结论、证据、风险和下一步，不回传完整探索日志。
- 禁止事项：是否允许编辑、运行命令、外部访问或高风险动作。

示例：

```yaml
description: 当已有代码改动需要审查时使用。只读取变更相关文件和必要引用，按严重性返回可执行问题、文件位置、证据和测试缺口；不做样式偏好审查，不直接修改代码。
```

## 回传格式

Subagent 输出必须优先服务主上下文卫生：

```markdown
## 结论
[一句话判断]

## 证据
- `path/to/file.ts:42`：[事实]

## 风险
- [风险及触发条件]

## 建议下一步
- [最小可执行动作]
```

不得回传大量 grep 原始输出、完整测试日志或目录树；需要保留时只给文件路径和复现命令。
