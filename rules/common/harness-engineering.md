# Agent Harness 工程

Harness 是模型外层的运行系统，不等同于 prompt、工具列表或多 agent。它负责把无状态模型变成可运行、可恢复、可验证、可治理的交付系统。

## 六个承重层

| 层级 | 关注点 | 检查问题 |
| --- | --- | --- |
| 主循环 | 输入组装、模型调用、工具执行、终止条件 | 是否能避免无限循环、过早结束、把中间结果误判为最终结果 |
| 工具系统 | 注册、参数校验、执行隔离、Observation 回写 | 工具失败是否明确回传，读写动作是否分层处理 |
| 上下文与记忆 | 工作集维护、长期线索、事实复核 | 记忆是否只作为线索，关键事实是否回到真实文件确认 |
| 状态与检查点 | 进度、恢复点、中间产物 | 长任务失败后是否知道从哪里继续 |
| 权限、错误与护栏 | 动作边界、确认机制、错误策略 | 高风险动作是否先区分“模型想做”和“系统允许做” |
| 验证与纠偏 | 测试、lint、类型检查、截图、审查 | 是否有外部反馈闭环，而不是只靠模型自评 |

## 一轮执行循环

复杂任务必须能说明当前处于哪一步：

1. 组装输入：读取必要规则、任务、工具定义、关键文件和当前状态。
2. 模型推理：决定直接回答、继续探索还是调用工具。
3. 分类输出：区分最终答复、工具调用、计划更新和阻塞问题。
4. 执行工具：先校验参数和权限，再决定并发读、串行写或拒绝。
5. 回写结果：把成功、失败、路径、证据整理成可继续推理的 Observation。
6. 更新状态：记录已完成项、关键决策、检查点和剩余风险。
7. 终止判断：按完成标准、预算、最大轮数、用户中断或护栏结束。

## 设计取舍

- 先修 Harness，再怀疑模型。Agent 不稳定时，优先检查工具失败、上下文污染、验证缺失和终止条件。
- Harness 越厚，控制越强但成本越高；默认从薄 Harness 开始，只为真实失败模式加机制。
- 单 agent 优先；只有边界清楚、可并行、可压缩回传的任务才委派 subagent。
- 规则、skills、hooks、agents 都应编码工程判断，不把同一判断散落在多处。
- 每次新增规则或 agent，要同时说明触发条件、退出条件、验证方式和回滚方式。

## 落地清单

变更 Harness 配置前后，至少检查：

- [ ] 任务成功标准是否可验证。
- [ ] 是否有最小验证命令或人工检查步骤。
- [ ] 是否需要 checkpoint，checkpoint 保存什么、不保存什么。
- [ ] 是否有高风险动作需要用户确认。
- [ ] 是否引入新的上下文噪音或工具描述成本。
- [ ] 是否能从 README、规则索引或命令入口发现这项能力。
