# Fast Path

仅在单仓库、改动 ≤2 个文件、已有能覆盖改动的测试或验收命令，且不改变公共契约、不涉及鉴权、数据迁移或
不可逆副作用时使用。修复现有公开函数不自动升级；用户明确指定的流程和目标项目规则优先。微改只读取本引用，不自动加载
implement、TDD、调试的完整流程链。

1. 修改前检查 Git 分支、基线和 staged/unstaged/untracked；新功能、受保护分支或有覆盖用户改动的风险时，
   先按 `rules/05-git-workflow.md` 完成必要隔离。后续 Git 操作和外部写入仍按该规则及用户已有授权执行。
2. 用相关函数和失败断言定位，定位后只读必要片段并直接修改；不先写 Spec、ticket、计划或总结文档，用户明确要求的流程除外。
3. 按 `rules/common/testing.md` 选定验证集：复现原问题、验证修复及受影响模块，并检查本次变化的兼容边界。
   最终状态已被较宽检查覆盖时不重复跑目标测试；仅在相关代码、配置、依赖和环境未变时复用结果。
4. 交付前按 `skills/code-review/SKILL.md` 做相称审查，低风险可自审；其余规则和 Skill 仅在用户明确指定、
   项目要求或当前决策需要时读取。
5. 完成时只说改了什么、跑了什么、结果和剩余风险。

以下任一条件触发时，回到 `skills/using-superpowers/SKILL.md` 的 Routing 选择入口：

- 同一失败连续 2 次未消除（预期的回归测试 RED 除外）。
- 改动面超过 2 个文件，或需要改变公共契约、鉴权、数据迁移或不可逆副作用。
- 没有能覆盖改动的可运行测试或验收命令。
- 必要隔离、安全、授权、审查或验收条件无法满足。

升级只补充当前决策需要的步骤，不重走已完成流程。构建、全量回归、E2E 按改动风险、受影响依赖、项目验收合同和相关质量门
决定，完成或提交本身不把局部修复升级为发布检查；本地交付也须满足适用质量门。已确认向后兼容的类型标注放宽或新增
可选参数不自动视为高风险边界。

命令软预算为探索 ≤4 条（不含依赖安装）、验证 ≤3 条；超出前说明已有证据的缺口，然后补充必要检查。
