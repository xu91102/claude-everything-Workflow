# 项目验收能力

用于明确授权的建立或维护请求。

## 1. 从项目事实确定入口

读取目标项目指令、启动配置、现有测试和自动化辅助代码，确认：

- 用户实际使用的界面：Web、Electron、移动端、CLI、服务/API 或库；多个界面分别列明。
- 启动与就绪信号、测试账号/数据、依赖服务，以及可观察结果。
- 可复用的驱动、选择器、日志和截图入口；先运行已有命令，不另造同功能 CLI。
- 端口、数据目录、账号和进程的隔离能力。不能隔离时串行，不共用用户正在使用的实例。

只询问项目中无法查明且影响结果的用户决策。缺环境或权限时标记 `BLOCKED`；产品行为不符合预期则 `FAIL`。不擅自安装系统工具、修改生产配置或扩大为产品修复；可记录草稿和缺口，但不能宣称验收能力已可用。

## 2. 保存项目本地操作契约

优先更新项目已有验收文档/Skill，并沿用其路径；没有入口时，在项目使用的 Skill 目录创建 `verify-<project>/SKILL.md`（含 name、description）及 `references/features.md`。宿主未使用项目 Skill 时放入项目约定的文档目录，并从已有项目入口链接。不要写进 CEW 的通用规则或用户全局 Skill。维护时保留人工内容，先核对差异，避免全量覆盖。

操作契约须让没有上下文的 Agent 直接使用，包含实际验证过的命令和工作目录，不留假命令：

| 内容 | 最低要求 |
| --- | --- |
| 启动 / 健康检查 | 构建和启动入口、就绪条件、目标版本、所属实例、账号是否可用；短命令程序可用一次真实调用确认健康 |
| 操作 | 真实用户入口和稳定定位方式；CLI/API/库使用公开接口，UI 不用内部状态注入代替操作 |
| 观察 | 等待真实完成信号，核对用户可见结果及必要的文件/数据副作用；相关错误不能被忽略 |
| 证据 | 基线、动作、结果、命令退出码、代码及用例版本；脱敏后保存至忽略目录，报告引用可回读的路径 |
| 清理 | 只关闭本次拥有的进程，移除本次创建的临时状态；保留证据，不按进程名批量终止 |

仅当缺少可复用入口且重复操作确有收益时，增加最小项目本地 helper。使用项目已有语言/依赖；复杂或多平台需求才扩展。必须实际运行 helper，验证失败退出码及清理路径；`--dry-run` 也要观察其副作用，不能凭名字认定安全。

## 3. 建立功能地图

先覆盖最主要的 3～5 个用户流程；项目更小则覆盖实际存在的流程，不凑数。地图不是测试通过清单，明确标注已验证与未验证部分。每个功能记录：

```text
功能 / 用户目标：
入口与子流程：列出需要覆盖的不同入口，不只列最方便的一个
前置条件：平台、服务、账号、数据及隔离要求
驱动步骤：引用实际命令/定位方式；写明输入与完成信号
成功断言：用户能观察到的结果及必要副作用
风险边界：错误、权限、空状态、恢复等与功能相关的用例
最近验证：代码/工具/用例版本、环境、日期、结果及证据位置
未覆盖项：具体入口或场景，以及原因
```

选择用例时结合改动、调用方和用户目标；地图是导航，不是范围上限。新功能或遗漏的关键入口必须补充。维护请求只检查相关条目与当前实现的漂移，不默认重写整份地图。

## 4. 实际执行后交付

按生成或修改后的说明完成一次闭环：启动 → 健康检查 → 一个真实核心流程 → 核对断言和证据 → 清理 → 再次打开证据。失败运行也执行所属资源的清理，保留失败证据；修正工具后重跑受影响步骤。维护时重跑受影响流程，不能用历史证据覆盖本次变化。

沿用主 Skill 的 `PASS / FAIL / BLOCKED / NOT RUN` 与二次审核要求。区分“验收入口已通过所列流程验证”和“整个产品通过验收”：一个流程跑通不代表整张地图通过。报告生成/更新的入口、已执行流程、证据、未覆盖项和后续调用方式；未执行的草稿不得作为已验证能力交付。

只有用户或项目合同要求时才接入日常开发验收；不自动新增 CI、定时任务、自动合并或发布权限。
