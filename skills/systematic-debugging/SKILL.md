# Systematic Debugging

## 分级入口

- 已确认失败原因正确的预期 TDD RED：回到实现的 GREEN，不加载完整诊断参考。
- 原因已由错误信息和调用链证实的普通失败：最小修复并重跑对应验证，不制造多个假设。
- 根因不明、修复后仍重复失败、flaky 或性能回归：进入下方证据闭环，同时读取
  `references/diagnosing-bugs.upstream.md`，仅查阅复现、最小化和回归方法；执行流程与退出条件由本文定义。

所有路径都保留原始症状和修复后的验证证据。不能把非目标错误当作预期 RED，也不能跳过真实失败。

## 证据闭环

1. **固定问题与现场。** 记录用户的实际/预期行为、发生时间、运行版本与环境，读取完整错误和相关改动。
   核对被测进程或产物确实对应目标版本；测试报错只有命中原症状才算复现。展示日志、请求和命令前脱敏。
2. **追踪实际调用链。** 从异常值或状态沿调用者反向追到首次偏离预期的位置，核对输入、输出、配置和状态。
   多组件问题先找最后正常边界与最早异常边界，再深入故障组件；对照正常样本或版本。
   区分报错位置、直接原因和上游触发条件，不能仅凭错误名称认定根因。
3. **选择取证路径。** 可复现时建立命中原症状的反馈并缩小场景；偶发问题记录样本数、失败率和条件，
   不以一次成功认定修复，也不强求秒级运行或固定复现率。无法重现时，继续关联已有 trace、日志、请求、
   时间线及代码路径，并用局部实验或定向观测检验解释；局部实验不冒充原场景复现。
4. **提出并检验假设。** 按现有证据选择有区分价值的假设，不凑固定数量。每个待检验假设写清依据、
   可推翻它的预测和最小实验；一次改变一个变量。执行后记录实际结果，标记支持、排除或仍未确定。
   展示假设是进度更新，不能在仍有可执行调查时以“可能原因”列表结束。
5. **确认后修复。** 进入根因修复前，说明触发条件如何沿调用链造成原症状，并提供能区分主要竞争解释的
   运行证据或对照实验。只有代码猜测、错误消失或重试成功不足以确认。证据不足时继续取证；用户要求先止损时，
   将措施标为缓解，不宣称根因已修复。确认后按上游方法执行最小修复和原始场景回归。
   尚未找到合适测试入口时，记录验证缺口并检查更完整的调用场景；缺少测试入口本身不能证明架构有错。
6. **失败后重新调查。** 假设被否定或修复无效时，记录反证，回到现场与调用链，不在未证实的改动上叠加补丁。
   连续三次修复无效，或修复不断引出不同组件的异常时，重新检查问题模型、环境和共享状态/耦合；
   次数只提示重新审视策略，不能证明架构有错或禁止继续调查、修复；超出授权范围的架构变更先提交具体证据和决策。

调查预算、信息增益与压缩边界见 `rules/common/agent-orchestration.md`；有有效新路径时继续，不因第四次调查而停止。

## 退出与报告

- **根因已确认：** 给出触发条件 → 因果链 → 原症状、关键证据及主要替代解释的检验结果。
  仅要求诊断时可到此结束；要求修复时还须报告最终状态的原场景验证，区分已定位、已修复和已验证。
- **尚未确认且可继续：** 执行下一项能区分假设的调查，不用置信度措辞代替证据。
- **受阻：** 已用尽当前可访问的有效取证路径，列明已尝试的方法、已确认的边界、缺失的具体证据及其获取方式，
  只请求必要的访问或用户操作。环境、时序或外部服务也需要证据，不能作为排查不到的兜底解释。

修改本流程后，用 [诊断场景](references/diagnostic-scenarios.md) 检查实际决策；仓库静态验证只证明文件与结构有效，
不能证明模型已能找到根因。
