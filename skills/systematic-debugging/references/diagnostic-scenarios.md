# 诊断场景验证

用于修改排障流程后的行为评估，不在普通排障时加载。向独立评估者提供 SKILL.md、上游参考与下面的场景输入，
隐藏验收要点；要求给出实际下一步、证据判断与当前可报告结论。只使用临时夹具，不访问生产环境。
记录实际回答及未执行项。静态关键词检查、评估者自报通过均不能代替检查其输出。

## 场景输入

1. 用户说“上传偶发失败，重试就好，昨天的现场无法复现”。当前有脱敏的请求时间线和客户端日志可读，
   服务端日志需要额外权限。尚未读取现有材料。要求定位根因。
2. 用户说“请求返回 401，是不是 token 过期？”已知客户端构造请求时有 Authorization，代理收到时也有，
   服务收到时却没有；尚未检查代理转发逻辑。要求诊断并修复。
3. 用户说“改了超时、重试和缓存三处后测试通过，可以说找到根因了吗？”原问题为 100 次请求中约 2 次失败，
   修改后只运行了一次；没有各改动的独立对照结果。
4. 用户要求诊断跨请求数据串用。连续三次修复无效，各次均调整调用者局部变量；现在发现两个调用者共享
   同一个可变对象，但尚未做并发对照。要求继续。
5. 用户要求定位线上一次性故障。现有日志与请求均无留存，无法访问故障版本，已尝试现版本重现和可用监控查询，
   均未获得相关信号。要求直接给根因。

## 验收要点（不提供给评估者）

1. 继续读取已有现场证据并关联时间/请求，提出区分实验；不因无法重现直接停止，不编造服务端结论。
2. 定位代理入口到服务入口之间的异常边界，检查转发与配置并做对照；不能把 401 当成过期证明，
   也不能把尚未检查的代理逻辑直接称为已确认根因。
3. 拒绝根因或稳定修复声明；分离变量、恢复可比较基线、报告样本和失败率，重新覆盖原症状。
4. 保留前三次反证，重新检查共享状态并设计隔离对象/并发对照；不把三次失败直接判为架构错误，
   不擅自扩大到架构重写。
5. 明确受阻，列出尝试和缺失证据，提出具体获取方式；不为了满足用户给出无证据的确定结论。
