# Issue Triage

只处理外部进入的 Issue/PR；`to-tickets` 产出的工单已经 ready，不重复 triage。远程读取可自动
进行，改 label、评论或关闭前必须得到用户对本轮动作的明确授权。

所有发到 tracker 的文字以此免责声明开头：

```text
> *This was generated by AI during triage.*
```

## Roles

每项恰好一个 category：`bug` 或 `enhancement`；恰好一个 state：

- `needs-triage`：待维护者评估；
- `needs-info`：等待报告者提供可行动信息；
- `ready-for-agent`：事实充分并有 durable brief；
- `ready-for-human`：仍需人工判断、权限或手测；
- `wontfix`：已实现、无效、重复或明确拒绝。

若当前 labels 冲突，停止并请求维护者裁决。项目实际 label 映射来自
`docs/agent-workflow/project-context.md`。

## When to Use

维护者要求查看、分类、核验或推进外部 Issue/PR 时使用；不处理本流程自己生成的 tickets。

## How It Works

### Discover the queue

用户要求“显示需要关注项”或“哪些可领取”时，先按
`docs/agent-workflow/project-context.md` 配置的 tracker 执行只读查询：

1. 分别查询 `Unlabeled`、`needs-triage`、以及在最后一条 triage note 后报告者有新活动的
   `needs-info` 三桶；每桶 oldest first。
2. 展示各桶计数和每项一行摘要。PR 明确标 `[PR]`，Issue 标 `[issue]`。
3. discovery 只纳入配置定义的 external PR，排除 collaborator 的进行中 PR；用户明确点名的
   PR 不受此发现过滤限制。
4. 让维护者选择一项后才进入具体 triage。询问“可领取项”时单独查询
   `ready-for-agent`，展示计数、oldest first 摘要和是否已有 durable brief，不改变状态。

### Triage one item

1. 读取完整正文、评论、labels、作者和时间；PR 还要读取 diff。
2. 搜索代码中的同域行为，检查是否已实现；读取配置的 `out-of-scope` 知识库以识别既有拒绝。
3. 给出 category/state 推荐、代码证据与预期远程动作，等待用户方向。
4. 验证主张：bug 用最小复现，PR 用相关测试与 diff 证据。记录 confirmed、failed 或
   insufficient detail。
5. 仅在 consequential decision 未解决时联合 `grilling` 与 `domain-modeling`；不重问已有答案。
6. 应用获批结果：
   - `ready-for-agent`：发布目标、证据、范围、acceptance、验证命令和风险；
   - `ready-for-human`：同上并写清不能委派的原因；
   - `needs-info`：列出已确认事实和对报告者的具体问题；
   - `wontfix`：已实现则指向代码；拒绝 enhancement 才写 `out-of-scope` 后关闭；
   - `needs-triage`：只设置状态并保留已有进展。

维护者明确要求 quick override 时，可跳过访谈，但在发布不完整 `ready-for-agent` brief 前
确认是否补齐 brief。恢复会话必须读取旧 triage notes，不重问已解决问题。

## Example

“显示需要我关注的项”先返回三桶计数与 oldest-first 摘要；“核验 #42 是否可复现，并建议
下一状态”则读全量 tracker context，再给推荐和获批动作。

## Exit

内部生成 ticket 返回 `NOT_APPLICABLE`。其他情况返回 `TRIAGE_RECOMMENDATION`、
`TRIAGE_APPLIED`、`NEEDS_INFO` 或 `BLOCKED`，附证据和远程变更。
