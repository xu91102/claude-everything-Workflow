# Grill Me

通过短而有压力的追问暴露关键假设。目标是尽快达到可执行状态，不是把访谈本身做成产物。

## When to Use

- 用户明确要求 grill、质疑方案或找盲点。
- 一个缺失答案会实际改变实现选择或验收标准。
- 低风险默认值不足以保护数据、安全、兼容性或核心用户体验。

能从代码、配置、测试、日志或文档中查明的事实，先自行查明。需求已经清楚时直接执行。

## How It Works

1. 阅读足以理解当前决策的最小上下文。
2. 在内部列出未知点，按“答案会改变实现”的程度排序。
3. 一次只问一个问题，选择影响最大且无法自行查明的那个。
4. 优先给 2-3 个互斥选项，并明确推荐默认值及其影响；开放题只在选项会误导时使用。
5. 收到回答后更新已知条件。只有下一个答案仍会改变关键决策时才继续。
6. 达到退出条件后，简要总结已确认决策、采用的低风险默认值和验证标准，然后交回最小充分路径。

## 问题预算

- 默认最多提出 3 个问题。
- 用户明确要求深度 grill，或任务涉及不可逆数据、安全、权限、合规风险时，可以超过预算。
- 达到预算仍有关键未知点时，不继续零散发问；改为说明剩余风险，并建议进入 `skills/brainstorming/SKILL.md`。
- 不把同一主题拆成多轮措辞不同的问题，不询问偏好性细节来填满预算。

## 退出条件

满足任一条件即停止追问：

- 已没有会改变实现或验收的阻塞未知点。
- 剩余未知点可采用可逆、低风险默认值，并已明确告知用户。
- 用户要求按当前信息继续，且不存在必须确认的高风险动作。
- 问题已升级为需要正式方案比较的高风险设计工作。

退出后：清楚且可回退的工作直接实现；协调复杂时按需写 plan；高风险正式设计才进入 `skills/brainstorming/SKILL.md`。不自动创建 spec，不要求额外批准。

## Examples

- “给登录接口加限流”且仓库没有限流策略：先问超限行为，因为答案会改变 API 契约。
- “把按钮文字改成保存”：不追问，直接修改并验证。
- “把单体数据库拆成分片”：简短问题无法控制迁移风险，转入正式设计。
