# 提示模式

这些模板是起点，不是固定格式。根据用户任务、仓库上下文和风险等级裁剪。

## 选择导航

按场景选模式；“对应规则”使用稳定标签，避免 SKILL.md 增删条目后编号失效。

| 场景 | 使用模式 | 典型产物 | 对应规则 |
| --- | --- | --- | --- |
| 不熟悉领域、模块或风险面 | 盲点扫描 | `unknowns.md` | 陌生任务 |
| 用户不知道该领域“好的标准”长什么样 | 盲点扫描（先教领域） | `unknowns.md` | 领域标准 |
| 用户说“我看到才知道” | 头脑风暴与原型 | `prototype.html`、方案草图 | 看到才知道 |
| 单个答案可能改变架构、数据、API、UX、灰度或安全 | 访谈 | 开放决策列表 | 架构影响 |
| 用户说不清但能指出示例、截图、源码或文档 | 参考物 | 映射说明 | 强参考物 |
| 即将触碰生产代码或多文件改动 | 实施计划 | `implementation-plan.md` 或 `.html` | 生产改动 |
| 实现中发现边界或偏离 | 实现记录 | `implementation-notes.md` 或 `.html` | 实现未知 |
| 大改后需要评审理解 | 说明文档、测验 | `explainer.md`、`quiz.md` | 实现后闭环 |

## 盲点扫描

```text
我正在做 [任务]。我当前确定的内容是 [已知的已知]。我不熟悉或还没想清楚的是 [已知的未知/经验水平]。

请做一次盲点扫描：如果有相关代码或文档，先检索它们；然后识别我的未知的未知，解释每个盲点为什么重要，并建议在实现前最低成本的验证方式。
```

输出形状：

```markdown
## 已知的已知
- ...

## 已知的未知
- 问题：
  重要性：
  低成本检查：

## 可能的未知的未知
- 盲点：
  证据/来源：
  风险：
  低成本检查：

## 下一步最合适的工件
- 建议：
- 原因：
```

## 头脑风暴与原型

```text
在触碰生产代码前，请为 [问题] 做 [N] 个明显不同的方案。目标是让我能对自己还说不清的取舍做反应。

每个方案都要给出工件或具体草图，说明它能帮助我们学到什么，以及如果选它，实现方案会发生什么变化。
```

UI、工作流或内容任务优先用单文件 HTML 原型或可截图 mock，加假数据即可。后端或架构任务优先用简短设计草图、API 示例、状态机图或迁移表。

## 访谈

```text
围绕 [任务] 中的歧义点逐个问题访谈我。只优先问那些答案可能改变架构、数据模型、API 合约、UX 流程、灰度策略、安全边界或测试策略的问题。

每得到一个回答，就更新开放决策列表，然后问下一个影响最大的问题。
```

当剩余问题影响很小，或可以通过仓库检索自行解决时停止。

## 参考物

```text
把 [参考路径/链接/示例] 作为 [具体行为、风格、语义或质量标准] 的事实来源。先阅读它，再提出实现方案。

告诉我哪些细节必须保留，哪些只是偶然实现，以及你会如何映射到当前代码库。
```

强参考物包括源码、测试、设计组件、线上示例、API 文档、事故复盘，以及带交互说明的截图。

## 实施计划

```text
为 [任务] 写一份实施计划。开头先放我最可能调整的决策：数据模型、类型/接口变化、UX 流程、API 行为、灰度和风险处理。机械编辑放到最后。

包含假设、仍然开放的未知项、验证步骤，以及如果实现中发现冲突约束时你会怎么处理。
```

推荐结构：

```markdown
## 目标
## 需要审阅的决策
## 假设与开放未知项
## 拟定实现
## 偏离处理策略
## 验证
## 机械编辑
```

## 实现记录

```text
请维护一个 implementation-notes.md 文件。如果遇到迫使你偏离计划的边界情况，只有在选择可逆时才自行采用保守方案，并记录到 Deviations。若偏离会改变用户可见行为、数据形状、安全或架构，请暂停让我审阅。
```

建议结构：

```markdown
# 实现记录

## 计划快照
## 发现
## 偏离
## 保守选择
## 暂缓问题
## 验证证据
```

## 说明文档

```text
把结果整理成面向评审者的说明文档。先展示 demo 或行为变化，再解释上下文、关键决策、处理过的未知项、验证证据和剩余风险。
```

推荐结构：

```markdown
## 改了什么
## 为什么这样做
## Demo 或前后对比
## 关键决策
## 已解决的未知项
## 验证
## 剩余风险
## 评审清单
```

## 测验

```text
请创建一个短测验，检查我是否已经充分理解这次变化，可以做 approve 或 merge 决策。问题要基于真实 diff、行为、现有代码路径和验证证据。答案单独放在问题之后。
```

测验重点放在行为、失败模式、灰度、兼容性、数据正确性和如何排查回归。
